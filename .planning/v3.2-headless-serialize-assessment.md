# v3.2 Migration Assessment — `@xterm/headless` + `@xterm/addon-serialize`

> Replace the raw-byte `session.scrollback` buffer with a server-side headless
> xterm.js terminal that maintains a real screen+scrollback grid. On phone
> reconnect, send a serialized snapshot instead of the raw byte history.
> This is the architecture VS Code / code-server uses.

**Status:** proposed. Not started. v3.1.7 ships the simpler truncation-at-clear-screen fix as a stop-gap.

---

## TL;DR — verdict per layer

| Layer | Impact | Risk |
|---|---|---|
| Claude Code CLI (laptop) | None — same PTY contract | None |
| WSL bash + dtach | None — server still drives the PTY | None |
| Server: PTY → buffer | **Replaced** — buffer becomes a virtual terminal | Medium (integration) |
| Server: WebSocket sender | Same wire format, smaller payload on reconnect | Low |
| E2E encryption (ECDH + AES-GCM) | **No change** — encryption wraps the new payload identically | None |
| Auth (WebAuthn / TOTP / identity key) | **No change** | None |
| Tailscale transport | Slightly less data on reconnect | Positive |
| iPhone Safari xterm.js | Receives a smaller, cleaner replay; same `term.write` API | Low |
| User-visible behaviour | Banners stop stacking; live cursor preserved on reconnect | Positive |
| Animation fidelity on reconnect | Lose intermediate frames (final state survives) | Acceptable |

**Net:** structurally better, no security or auth regression, modest memory shift, real integration risk concentrated in three places (resize plumbing, dtach recovery, deploy migration).

## 1. Pipeline today vs. v3.2

### Today (v3.1.7)
```
Claude Code (cmd.exe /c claude inside WSL bash)
    │ stdout/stderr (ANSI bytes)
    ▼
dtach socket  ──► node-pty (server.js)
                       │ proc.onData(data)
                       ▼
                session.scrollback += data         ◄─── append-only string, 400 KB cap
                       │                                 + truncate at \x1b[2J / \x1bc / \x1b[3J (v3.1.7)
                       ▼
              broadcast to all connected ws.clients
                       │ secureSend (AES-GCM, ECDH session key)
                       ▼
                 Tailscale tunnel (WireGuard)
                       ▼
              iPhone Safari WebSocket → secureReceive → term.write(data)

ON RECONNECT:
  server: send full session.scrollback (raw bytes)
  client: term.reset() + chunked term.write(50 lines at a time)
```

### v3.2
```
Claude Code (unchanged)
    │
dtach socket  ──► node-pty (unchanged)
                       │ proc.onData(data)
                       ├─► session.headless.write(data)        ◄─── NEW: headless xterm parses bytes
                       │                                            into a virtual screen+scrollback
                       │                                            grid (no raw byte buffer)
                       ▼
              broadcast LIVE bytes to ws.clients (UNCHANGED)
                       │ secureSend
                       ▼
                 Tailscale → iPhone → term.write (UNCHANGED)

ON RECONNECT:
  server: const snapshot = session.serializer.serialize({ scrollback: 1000 })
          send { type: 'scrollback', data: snapshot }      ◄─── compact ANSI stream that
                                                                reconstructs the current screen
                                                                + N rows of real history
  client: term.reset() + term.write(snapshot)              ◄─── single write, no chunking
```

The live-streaming path is **unchanged**. Only the buffer-and-replay layer changes.

## 2. What changes, file by file

### `package.json`
Add two deps:
```json
"@xterm/headless": "^5.5.0",
"@xterm/addon-serialize": "^0.13.0"
```
Both maintained by the xterm.js team (Microsoft). MIT licensed. ~150 KB added to `node_modules`. Pure JavaScript, no native bindings — won't complicate the WSL/Windows install.

### `server.js`
Three areas:

1. **Session create** (around `wireSessionProc`):
   ```js
   const { Terminal } = require('@xterm/headless');
   const { SerializeAddon } = require('@xterm/addon-serialize');
   // ...
   session.headless = new Terminal({ cols, rows, scrollback: 1000, allowProposedApi: true });
   session.serializer = new SerializeAddon();
   session.headless.loadAddon(session.serializer);
   ```

2. **PTY data handler** (line ~1096):
   ```js
   session.proc.onData((data) => {
     if (session.generation !== gen) return;
     session.headless.write(data);                    // NEW: feed virtual terminal
     // session.scrollback += data;                   // REMOVED (or kept as fallback for one release)
     // ... rest unchanged: broadcast to clients, attention timer, etc.
   });
   ```

3. **Reconnect handler** (line ~1483):
   ```js
   case 'connect': {
     // ...
     if (session.headless.cols > 0) {
       const snapshot = session.serializer.serialize({ scrollback: 1000 });
       secureSend(ws, { type: 'scrollback', session: session.id, data: snapshot });
     }
     // ...
   }
   ```

4. **Resize handler**: every time the client sends `{ type: 'resize', cols, rows }`, also resize the headless terminal:
   ```js
   session.headless.resize(cols, rows);
   ```
   Critical — if the headless term's dims drift from the actual PTY's dims, the snapshot will be malformed.

5. **Session destroy**: `session.headless.dispose()` to free memory.

6. **dtach recovery** (line ~1210): when recovering existing dtach sessions after server restart, instantiate a fresh headless term. Initial state will be empty until live bytes flow in. Acceptable — a recovered session shows current screen on first reconnect, just like a fresh attach to dtach would.

### `public/index.html`
Minimal change in the `case 'scrollback':` handler (line ~789):
```js
case 'scrollback':
  if (terms[m.session] && m.data) {
    terms[m.session].reset();
    terms[m.session].write(m.data);          // single write, no chunking
    terms[m.session].scrollToBottom();
  }
  break;
```
The chunked replay was a workaround for large raw byte dumps causing UI lag. Serialized snapshots are typically 5-50 KB, fast to write in one call.

## 3. Memory & CPU

### Memory
- **Today:** 400 KB string max per session. With 5 sessions = 2 MB.
- **v3.2:** virtual grid + scrollback. At cols=46, rows=40, scrollback=1000:
  - Cell storage in xterm.js is ~16 bytes/cell with attributes
  - 46 × (40 + 1000) × 16 ≈ **766 KB per session**
  - 5 sessions = **3.8 MB**
- Net: roughly **2x memory per session**. Still small in absolute terms — your laptop has GB to spare.

### CPU
- xterm.js parser is fast (it parses every byte going to your iPhone today, just on the client). Now it parses on the server too.
- Benchmark from xterm.js: ~50 MB/s of ANSI throughput on a single thread. Claude Code emits maybe 10 KB/s peak. **CPU cost is negligible.**
- Reconnect: serialize() runs once per reconnect. Should complete in <50 ms even for full-scrollback snapshots.

### Network (Tailscale)
- **Today:** reconnect can dump up to 400 KB of raw bytes
- **v3.2:** serialize() output for a typical screen is **5-50 KB**. Bigger win on phone reconnect over cellular.

## 4. Security & protections — *no regression*

I've audited each layer. Nothing in the v3.2 plan touches the security primitives.

| Mechanism | Affected? | Why not |
|---|---|---|
| **ECDH P-256 key exchange** | No | Headless terminal sits before `secureSend`. Wire format is still ECDH-derived AES-GCM. |
| **AES-256-GCM payload encryption** | No | Same `secureSend` envelope wraps the snapshot exactly like it wrapped the raw bytes. |
| **Identity key TOFU fingerprint** | No | Server identity key file untouched. |
| **TOTP secret + backup file** | No | Untouched. v3.1.7's hardening (atomic writes, backup recovery, graceful shutdown) intact. |
| **WebAuthn / Face ID** | No | Untouched. |
| **Session tokens, TTLs, IP-binding** | No | Untouched. |
| **Localhost-only setup** | No | Untouched. |
| **Audit log** | No | Continues to log scrollback events. May want to add `audit('SCROLLBACK', \`serialized N bytes\`)` for parity. |
| **Rate limiting** | No | Untouched. |
| **Canary tokens / suspicious input detection** | No | Headless term doesn't reduce visibility — live `data` still flows through `updateRecentOutput` and `checkCanary`. |

**The headless terminal does not introduce a new attack surface for clients.** It only consumes bytes from the PTY (which we already trust as system output) and produces a serialized stream that flows through the same encrypted channel. No new parsing of *user* input.

**One thing to consider:** the headless terminal is itself code that parses untrusted ANSI input from the PTY. xterm.js has had occasional parser CVEs (rare — and these are typically client-side concerns since the consumer is a browser). Running it server-side means a maliciously crafted ANSI sequence could in principle exploit a parser bug to crash the Node process. Mitigations: it's the same parser the *client already runs*, so attack surface in the system as a whole isn't really expanded; xterm.js is actively maintained; PM2 restart on crash gives resilience.

| Multi-session (8 parallel) | Yes | Yes | Each session gets its own headless term |

| Dynamic slash-command discovery | Yes | Yes | Unchanged |

| **History preserved across TUI restarts** | No (v3.1.7 truncates) | **Yes** | Real scrollback rows survive even when the visible screen is cleared |

## 6. Risks and how to handle them

### Risk 1: Headless term dims drift from PTY dims
**Symptom:** snapshot has wrong cols, lines wrap weirdly on the client.
**Mitigation:** every `resize` message AND every `dtachInit/proc.resize` call must also call `session.headless.resize(cols, rows)`. Add a unit-style test: after a sequence of resizes, assert `session.headless.cols === lastCols`.

### Risk 2: UTF-8 split across chunks
**Symptom:** garbled multi-byte chars in snapshot.
**Mitigation:** xterm.js handles partial UTF-8 internally — it buffers incomplete bytes and processes them with the next chunk. Verify with a smoke test that emits `🤖` mid-banner.

### Risk 3: Memory leak from undisposed sessions
**Symptom:** Node RSS grows over days.
**Mitigation:** every place that calls `session.proc.kill()` or removes from `sessions` map must also call `session.headless.dispose()`. Add an audit log line. Watch RSS in PM2 for a week post-deploy.

### Risk 4: Resize during serialize race
**Symptom:** client receives a snapshot for the wrong size.
**Mitigation:** xterm.js parsing is synchronous. As long as `resize` and `serialize()` aren't interleaved within an event-loop tick, you're fine. Don't make `serialize()` async or yield mid-call.

### Risk 5: Deploy disrupts live sessions
**Symptom:** users connected during the deploy lose history.
**Mitigation:** dtach sessions survive server restart (current behaviour). After v3.2 deploy, recovered sessions start with empty headless terms — first reconnect shows current screen only, no pre-deploy history. **One-time disruption per session, then back to normal.** Document this in the changelog.

### Risk 6: Snapshot includes secrets
**Symptom:** if Claude Code printed an API key, it lives in the snapshot until the screen scrolls past it.
**Mitigation:** same exposure as today's raw scrollback. No worse. The headless term *could* be configured with `scrollback: 100` instead of 1000 to reduce window. Decide based on user preference.

## 7. Phased rollout (recommended)

Each phase is independently shippable and safe to roll back.

### Phase A — additive deps (commit, no behavior change)
- `npm install @xterm/headless @xterm/addon-serialize`
- Verify `npm install` works on Windows + WSL + macOS dev environments
- No code changes
- Ship as **v3.1.8**

### Phase B — instantiate headless terms in parallel (no replay change)
- Create headless term + serializer per session
- Feed `proc.onData` to the headless term *in addition to* appending to `session.scrollback`
- Add audit logging: log serialize() output size on every reconnect (without sending it)
- Compare logged size to the size of the raw scrollback that *was* sent
- Run for a week, watch memory, verify no crashes
- Ship as **v3.1.9**

### Phase C — switch reconnect to serialize (the actual feature)
- Replace `secureSend({ type: 'scrollback', data: session.scrollback })` with `serialize()`
- Keep raw scrollback buffer for one more release as a fallback
- Ship as **v3.2.0**
- User-visible behaviour change: banners stop stacking, real history preserved

### Phase D — remove raw scrollback (cleanup)
- Delete `session.scrollback` field
- Delete the v3.1.7 truncation code (no longer needed)
- Ship as **v3.2.1**

Total effort: ~1 focused day for code, plus 2-3 weeks of soak time across phases. Or all-in-one over 1-2 days if you want to skip the safety net.

## 8. Open questions for you

1. **Scrollback depth on the phone:** today the xterm.js client has `scrollback: 10000`. Server-side I propose `scrollback: 1000` for the headless term (= what we replay on reconnect). Comfortable with that, or do you want more?
2. **Phased vs. one-shot:** are you OK with the 4-phase rollout, or do you want to ship v3.2 as a single commit? Phased is safer; one-shot is faster.
3. **Keep the v3.1.7 truncation code as belt-and-suspenders?** Once headless+serialize is in, the truncation is redundant. I'd remove it in Phase D for code clarity, but it's defensible to keep for resilience if the headless approach ever breaks.
4. **Test access:** do you want to add a server endpoint (localhost-only) that dumps the current serialize() output for a given session, so you can inspect what reconnects would see? Useful for verification, easy to add.

## Bottom line

**Pipeline-wide impact:** isolated to the buffer-and-replay layer. Every other layer (Claude Code, WSL, dtach, encryption, auth, Tailscale, client renderer) is untouched.

**Capabilities:** all current capabilities preserved. Three new wins (banner dedup, real history through restarts, smaller reconnect payload). One trade-off (animation frames lost on reconnect — usually invisible).

**Protections:** unchanged. Encryption, auth, and identity layers are above the change.

**Risk profile:** medium. Real integration work concentrated in resize plumbing, dispose lifecycle, and deploy migration. Manageable with the phased rollout.

**Recommendation:** ship it, but phased. Don't be in a hurry. v3.1.7 already solves the user-visible symptom; v3.2 is the architectural correctness pass.
